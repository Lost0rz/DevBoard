# Mac Native Setup V1 Contract

Status: frozen for the single-node Mac A dogfood milestone.

This contract is subordinate to and consistent with
`Docs/contracts/single-node-three-surface-product-v1.md`. It defines the
native first-run Mac surface only; it does not change the NAS Hub, Pad Display,
Node-to-Hub wire, or deferred multi-host contracts.

## 1. Scope and authority

Mac Native Setup V1 covers one physical Mac A using the existing per-user
LaunchAgent-owned Node and the existing secure product configuration
persistence. The first package remains **INTERNAL DOGFOOD DMG**. No real Mac,
LaunchAgent, Hook, Keychain, CodexBar, account, NAS, or Hub container is
modified by self-tests or build validation.

The LaunchAgent is the only background Node lifecycle authority. The menu-bar
App is a status and control client. Quitting, hiding, or losing the App must
not stop, unload, uninstall, or rewrite the LaunchAgent-owned Node.

## 2. Menu-bar surface

The first-level menu contains only:

1. Current connection status;
2. `Configure Mac…`;
3. `View Monitoring Display`;
4. `Open NAS Admin`;
5. `More…`;
6. `Quit`.

Current connection status uses text and an icon. The five required signal
labels remain visible in that status area: Node, Hub, Codex, Claude Code, and
Quota. Color alone is never a state indicator.

`More…` contains the secondary and recovery surfaces:

- Install/Repair;
- Restart Background Service;
- Open Browser Settings (advanced fallback);
- Integrations;
- Quota Setup;
- Logs;
- App login-item controls.

The App may open independent windows for Setup and Advanced surfaces. The
menu-bar App is an agent-style app (`LSUIElement`/accessory behavior) and does
not require a main window to remain open.

## 3. Configure Mac window

`Configure Mac…` opens a native SwiftUI setup window. Its normal surface
contains:

- an editable display name;
- a `SecureField` for the Node Token;
- a read-only Node ID;
- `Save & Test`;
- a bounded, actionable result message.

The NAS endpoint is initialized from the current product configuration. It is
shown only under Advanced controls in the setup window. The Node ID is read
from existing configuration or generated by the product from cryptographically
random bytes when no identity exists. The normal UI cannot edit it.

The first-run flow does not require a browser or Terminal. Browser Local
Settings remains available only as an explicit advanced fallback.

## 4. Save & Test boundary

`Save & Test`:

1. validates display name, endpoint, token, and Node ID identity binding;
2. reuses the existing secure config validation and atomic persistence;
3. writes the product-private config with private directory/file permissions;
4. asks the LaunchAgent service authority to install/repair or restart the
   background Node as appropriate;
5. waits within a bounded budget for the resulting local Node/Hub connection
   result and shows only a safe status class.

The token is accepted through a protected in-memory request boundary (stdin or
equivalent), never as a process argument. It is never returned in product
JSON, status APIs, logs, ordinary UI, error text, or process listings. An empty
token is rejected when no existing configured token can be preserved. An
existing configured token may be preserved when the user changes only the
display name; the token is never displayed back to the user.

The product must reject a request that attempts to change an existing Node ID
or otherwise breaks Node identity binding. A failed test produces a bounded
error and does not claim Connected/Healthy.

## 5. Testing and implementation seams

Native setup tests use dependency injection and temporary directories. They
must cover:

- first installation configuration;
- changing display name while connected;
- wrong token and bounded Save & Test timeout;
- empty token;
- Node ID identity binding;
- token absence from logs and process arguments;
- Quit isolation from LaunchAgent service lifecycle.

Service, network, and product-command test doubles must not call real
LaunchAgent, Hook, Keychain, CodexBar, account, or NAS resources.

## 6. Quota CLI resolution amendment (2026-08-25)

Quota Setup and the background quota collector invoke CodexBar through
absolute-path resolution, never a bare PATH lookup and never a shell:

1. well-known absolute candidates (`/opt/homebrew/bin/codexbar`,
   `/usr/local/bin/codexbar`) are checked first so the per-user LaunchAgent
   works with launchd's minimal PATH;
2. a PATH lookup remains the last-resort fallback for interactive use and
   must return an absolute executable path;
3. when no CLI can be resolved, the menu-bar Quota signal shows
   `CodexBar CLI unavailable` and the product reports
   `quota_cli_unavailable` — never a generic quota-unavailable label;
4. the identity key flow stays product-owned: a 32-byte key is generated at
   an absolute mode-0600 path inside a private mode-0700 product directory,
   never through a symlink, and the user never types an account key, edits
   YAML, or enters a token;
5. after the first successful Quota Setup the background Node must be
   restarted to load the collector; the configure result says so explicitly.

The LaunchAgent plist itself keeps no PATH dependency: resolution happens
inside the product process before exec.
